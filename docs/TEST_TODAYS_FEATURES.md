# Test the visit QR and medical-record features

This guide covers the features added on 6 November 2026. Use fictional data only. Patient IDs are stable; QR codes now belong to individual visits and are signed over patient ID, appointment ID, and visit date. Two appointments on the same day therefore have different codes.

## 1. Start the app

From the repository root, start the backend and frontend in separate terminals:

```powershell
npm --prefix server run dev
```

```powershell
npm --prefix client run dev
```

Open `http://localhost:5173/login`. Restart both services if they were already running with older code. Existing permanent patient QR images from the earlier prototype no longer work; refresh **My visit QR**.

The large dataset has already been inserted into the configured database for this checkout. To create it on another database or prepare appointments for another day:

```powershell
npm --prefix server run seed:large
```

The command preserves existing passwords, records, status changes, and file attachments. On the same day, reruns do not duplicate data or reset finished tests. On another date, it adds a new set of daily visits. It never deletes other data. All date checks use `HOSPITAL_TIMEZONE` (currently defaults to Asia/Dubai).

## 2. Get the demo logins

The large-demo accounts share the password generated by your seed run. Its value and the complete account roster are saved in the ignored local file `server/.demo-large-credentials.json`. To display only your local demo password:

```powershell
(Get-Content server/.demo-large-credentials.json -Raw | ConvertFrom-Json).password
```

No live password is stored in this public guide. The earlier small-demo accounts keep their original passwords.

| Role / scenario | Login | Facility / purpose |
|---|---|---|
| Main patient | `patient001@demo.hospiq.invalid` | Two active visits today, 12 prior records |
| Another patient | `patient002@demo.hospiq.invalid` | Use for wrong-person QR testing |
| Main doctor | `doctor01@demo.hospiq.invalid` | Dr. Demo Clinician 01, General Medicine, Harbour |
| Second doctor | `doctor06@demo.hospiq.invalid` | Dr. Demo Clinician 06, General Medicine, Oasis |
| Harbour staff | `staff01@demo.hospiq.invalid` | Queue and doctors for Harbour |
| Oasis staff | `staff03@demo.hospiq.invalid` | Verify cross-hospital queue isolation |

All accounts are fictional. General patterns are `patient001` through `patient120`, `doctor01` through `doctor30`, and `staff01` through `staff12`, all at `@demo.hospiq.invalid`.

**Use two independent browser sessions:** a normal window for the patient and an incognito window or another browser for the doctor. Two normal tabs of the same browser share localStorage and will overwrite each other's login. Sign out before switching roles in the same session.

## 3. Patient ID and visit-specific QR

1. Sign in as the main patient. The homepage shows **Patient ID & visit QR**; the same section is in Profile and **My visit QR**.
2. Note the `HQ-...` ID. This ID remains unchanged for every visit.
3. Use **Select today's visit** to select Dr. Demo Clinician 01 at Demo Large - Harbour Hospital. Note its date, status and token number.
4. Download its QR PNG or choose **Copy visit QR data**. Label this image/data **Harbour visit** for your test.
5. Select Dr. Demo Clinician 06 at Demo Large - Oasis Hospital. Download/copy that visit's code separately.
6. The two codes must differ even though the patient and date are the same. QR filenames contain the appointment ID so their downloads do not collide.

The first seeded Harbour visit is pending and the Oasis visit is called. If earlier testing changed them, use their current states; the seed intentionally preserves edits. Completed/cancelled/previous-day visits do not offer an active code. Without an active visit today, the patient sees their ID and instructions to book one rather than a reusable permanent QR.

## 4. Doctor scan, confirmation, and record entry

1. In the independent doctor session, sign in as `doctor01@demo.hospiq.invalid`.
2. On **Queue overview**, search for **Demo Patient 001**.
3. Select **Scan patient QR** on that patient's row.
4. Choose **Upload QR image** and use the Harbour PNG, or paste the Harbour code and select **Verify pasted QR**. Camera scanning is another option, but requires browser permission plus HTTPS or localhost.
5. Confirm the matched patient's name/ID, doctor, facility, department, date, and appointment number.
6. Choose **Start visit & add medical record**. The pending visit becomes called and its record form opens. A called visit opens entry directly.
7. Enter a visit reason, add one or more **Demo medications**, and fill in fictional prescription/visit notes. Date/time uses your browser's local time and is stored as an ISO timestamp.
8. Optionally upload `server/fixtures/demo-lab-report.pdf` as a lab report, then save.
9. Verify **Medical record saved**, the matching patient/doctor context, and your new record.
10. In the patient session, open **Medical records** and refresh. The new record and files should be visible.

The appointment is linked to the saved record. The clinical doctor's identity, department and facility come from the server, not editable QR data. Offline walk-ins without registered accounts cannot show a patient visit QR; their scanner is disabled with an explanation.

## 5. Check wrong-patient and wrong-visit rejection

Keep Dr. Demo Clinician 01's **Demo Patient 001** appointment selected:

- Upload or paste that same patient's **Oasis** visit QR. It must be rejected as the wrong visit/date; matching patient identity alone is insufficient.
- Sign the patient session out, sign in as `patient002@demo.hospiq.invalid`, and copy one of that patient's visit codes. Scanning it on Patient 001's row must be rejected as a different patient.
- Random text, a bare HQ ID, an old permanent QR, a tampered code, or an old appointment-ticket QR must not be accepted.
- Another doctor's queue cannot resolve your selected appointment. Staff do not have medical scanning privileges.

No failed scan should reveal clinical history or create a consent grant.

## 6. Prove the QR changes for the next visit on the same day

1. Keep a copy of the old Harbour QR.
2. Finish the Harbour appointment through **Complete visit** in the doctor queue (or cancel it as the patient if you have not started it).
3. The old visit stops offering a usable QR. Refresh the patient section if it still shows the older selection; it also polls every 30 seconds.
4. As Patient 001, book another appointment with the same Harbour doctor using **Find care**. Demo schedules are open daily 00:00-23:59; the end time is exclusive.
5. Select the new appointment in **My visit QR**. The patient ID and visit date stay the same, but the appointment ID and QR differ.
6. On the new appointment's doctor row, try the old code: it must fail. The new code must match.

Only one active booking per patient/doctor/day is allowed. Complete or cancel the first one before rebooking that doctor. Do not change your PC clock for date tests; the automated suite covers different dates and old-code rejection. Rerun the large seed on a later day to create that day's fictional queues.

## 7. Own-doctor records versus other doctors' records

Before adding new records, Patient 001 has 12 seeded historical records across local and external clinicians. The Harbour doctor initially sees two associated earlier records, while the Oasis doctor sees one. Other records remain hidden until permission is granted. Counts increase as you add your own test records.

1. Sign in as Patient 001: all 12 historical records and their protected attachments should be visible.
2. Sign in as the Harbour doctor: only that doctor's associated history plus any new records from their visits should be visible automatically.
3. Sign in as the Oasis doctor: they see their own associated records, not the Harbour doctor's private notes by default.
4. A staff login must not be able to open clinical-record routes. Harbour and Oasis staff queues should also stay separate.

## 8. Test OTP permission, expiry, and revocation

**The dummy `*.invalid` addresses cannot receive real email. No universal/demo OTP bypass exists.** Use one of these two paths:

### Automatic isolated verification

```powershell
npm --prefix server run test:records
```

This runs a real HTTP workflow against a uniquely named disposable database and a local SMTP fixture. It tests email capture, wrong/expired/exhausted/reused codes, wrong doctor, consent, revocation, expiry, mail failure without granting access, and visit QR matching. No real email is sent, and the temporary database/files are removed afterward. It does not replace a Gmail delivery test.

### Full UI/email test with your own verified address

1. Register a patient account using an email address you control and complete normal registration verification.
2. Add a fictional external visit in **Medical records**, including the sample lab PDF. Leave it external instead of associating it with the doctor you will consult.
3. Book a current visit with one of the demo doctors and show that visit's QR.
4. As the doctor, scan the matching QR and start the visit. Keep it pending/called until the consent test is finished; completed visits cannot initiate new permission requests.
5. On the record page select **Request patient permission**. The external record should remain hidden.
6. Check the patient's actual inbox. The email names the doctor/hospital and explains the 30-minute read-only scope. Share the six-digit code only if you approve this fictional test.
7. As the doctor enter that code. The external record and protected file should now be readable for 30 minutes.
8. As the patient, use **Doctors with temporary access → Revoke access**. The doctor's next API/file read is denied; the page refreshes its record view every 30 seconds and also has a Refresh button.
9. Confirm reusing the same OTP fails. Codes expire after five minutes and five failed attempts; a new code requires a new patient approval. Use the isolated suite to test expiry without waiting.

Revocation blocks future reads but cannot retract data already viewed or downloaded. Scanning the QR never bypasses this permission flow.

## 9. Upload / scan documents and download lab reports

- As a patient, use **Add visit / upload documents**. Enter doctor, department, facility and date/time. Choose external text fields or explicitly associate an upload with a Hospiq doctor and confirm that doctor's access.
- Use **Upload files** for JPEG/PNG/PDF or **Scan / take photo** on supported camera devices. This stores the document image, not automatic OCR.
- Maximum five files per record and 10 MB per file. Unsupported or mismatched file signatures should fail.
- Download a seeded lab attachment from your own record. These 480 files are encrypted on private storage; they have no public delivery URL.
- Without patient permission, another doctor must not download that attachment. Under an approved grant they may do so until expiry/revocation.

The sample PDF is clearly marked fictional and contains no clinical results. It is suitable for upload/download tests without using real medical documents.

| Item | Large-demo count |

| Facilities | 6 |
| Doctor profiles and linked doctor logins | 30 |
| Staff logins | 12 |
| Patient logins | 120 |
| Total user accounts | 162 |
| Weekly doctor schedules | 30 |
| Historical visits | 1,440 |
| Historical medical records | 1,440 |
| Encrypted lab-report attachments | 480 |
| Appointments for the seed run's date | 240 |

Departments are embedded in each facility: General Medicine, Cardiology, Paediatrics, Dermatology and Orthopaedics (30 facility-department entries, five distinct department names). Existing smaller demo data is preserved separately.

The daily queue intentionally mixes pending, called, skipped, completed and cancelled visits. Current limits include unpaginated histories, manual queue refresh, no SMS OTP, no OCR, and no real camera hardware coverage in automated tests.
